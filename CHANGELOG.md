# Changelog

## Unreleased

- Stops one install from publishing two opposite answers about one roam executable. `compile verify` and `compile doctor` refused an unsupported toolchain while `compile report`, `compile baseline` and `compile init` drove that same binary to completion and exited 0 in the same tree, from the same shell - `compile report` writing a PASS report from a toolchain the same install called unusable. The split was an ACCIDENT, established rather than argued: `_roam_problem` was born inside the verify sealing work, its own commit stated the requirement GLOBALLY, and no artifact in the tree or in its history records a decision to exempt any verb. It was never added to `_report` and never removed. The test written one commit earlier had then PINNED that accident with two exact set equalities plus an assertion whose only function was to forbid gating `report` - measured, gating a single verb failed BOTH equalities. The rule is now: a verb may skip the toolchain check only if it makes no assurance claim and writes no state a gated verb later consumes. `report` and `baseline` fail that test because compile-code's single contribution to them is adopting roam's exit code as its own, and at a product boundary the exit code IS the claim a CI job branches on; `baseline` additionally writes the accepted-debt file that tells `verify --new-only` which findings to SUPPRESS, so a roam the gate refuses to RUN was deciding what the gate ignores. `init` fails it because the index it writes is the substrate every later gated verify reads. All three now refuse with the same one-line verdict the other three already gave. `run`, `stats`, `wire` and `unwire` stay exempt ON PURPOSE and each carries its reason in cli.py, not only in a test: `run` and `stats` are advisory output that asserts nothing, and `wire`/`unwire` are the recovery path - refusing there means a user can neither install the loop that would report the problem nor un-wire one already failing on every agent turn. The pin is now one-directional in both places: gating MORE always passes, and a new delegating verb fails until someone lists it with a written reason. Demonstrated live against an out-of-interval roam: verify, doctor, report, baseline and init all exit 2 with one identical verdict, while run and stats still run; and against the supported roam every one of the six still completes with its normal verdict. What this does not close: persisted state has no version guard at all, so a `.roam/verify-baseline.json` or index written by an out-of-interval roam BEFORE this change is still read afterwards with no complaint, and closing the verb split stops future contamination only. `compile doctor` still reports verify-report freshness from the file's mtime alone and never reads the `roam_version` stamp inside it. `_delegate` still inspects nothing, so the four exempt verbs check neither floor nor envelope. And an exemption reason is asserted to be PRESENT and to name one of the two permitted grounds - nothing can check that it is true.

- Deletes the runtime product-major ceiling on roam, because it checked the wrong property and detected nothing. `MAX_ROAM_MAJOR_EXCLUSIVE` refused any roam whose PRODUCT major reached 14, and a product major is not the contract this CLI consumes. Measured against the real roam 14.0.0 binary: its verify envelope declares `schema_version` 1.2.0 - a MINOR bump ACROSS a product major bump - and its top-level key set is exactly `_VERIFY_ENVELOPE_KEYS` with zero additions, so roam's own contract said compatible while the ceiling said refuse. This is not a relaxation. Nine constructed drift mutations were run through the real verify path against a shim delegating to the real binary - rescaled scores, a relabelled severity, a re-defined `checks_run`, a gate exit code moved 5 to 3, a success exit code moved 0 to 3, a moved default threshold, a loosened PASS band, and two removed CLI flags - and seven were caught at exit 2 by the contract guards (`completion_binding`, `failure_contradiction`, `success_contradiction`, `invalid_json_document`). The ceiling caught none of them, because a version ceiling detects nothing: it defers the whole question to a human typing a bigger number, and the deferral ends at exactly the moment the risk arrives, since the only way forward is to type it. Raising it is measurably a treadmill - with the ceiling at 15 a roam reporting 15.0.0 produces the byte-identical outage one major later. What it cost was live, not hypothetical: on a machine with roam 14.0.0 on PATH, `compile verify` exited 2 with no verification at all while `compile report` drove that same binary to `VERDICT: PASS` in the same tree, from the same shell. The guards that read the actual contract carry this and are unchanged: a different ENVELOPE major still refuses (`envelope_schema_incompatible`), an unknown incompleteness-vocabulary key still refuses and names the field (`unknown_incompleteness_signal`), a neutral additive field still passes and is disclosed as unread, and every gate-determining value - verdict, score band, exit code, receipt binding, scope arithmetic - is still re-derived and cross-checked. Those three refusals were previously UNREACHABLE at a future major, because the ceiling exited before the envelope was ever parsed; they are now pinned end to end at a roam reporting 99.0.0. The remediation loses its second arm with the ceiling it described, so a version refusal again has one cause and one true fix. The exclusive ceiling that remains is the PACKAGING pin in `pyproject.toml`, raised 14 to 15 and still checked by `_floor_drift`: it is a resolver preference naming the newest major a receipt-v3 transaction has been run against, and going stale there costs a dependency resolution, not a user outage. What this does not close: two disclosure-level drifts that no guard catches - roam re-defining `checks_run` from "checks that ran" to "checks available", which would make the rendered `checks:` line a false claim about what was verified while the gate stays correct, and roam's DEFAULT threshold moving within a quality band when the caller passes no `--threshold`. The ceiling would have deferred both exactly once, to a human bump, after which they are uncaught anyway. Nor does it close the packaging pin being hand-maintained with nothing to announce it has gone stale, or the fact that removing a refusal is close to irreversible in public - re-adding a product-major refusal later would break users already on the newer major.

- Checks a cardinality stated in prose against the constant it names, and corrects the one that shipped wrong. The entry below overstated the size of `_VERIFY_INCOMPLETENESS_NAMES` by three: it holds 33 names, not 36. The false number went into this file — the one tracked file where this project's public numbers live — one commit after the gate for exactly this class landed, and that gate could not see it for two independent reasons rather than the one that is obvious. It reads only tracked `*.py`, AND the claim matches neither its quantity pattern (whose nouns are commits, blobs, candidates, files and byte units — `names` is not among them) nor its live-repo referent. Measured both ways: widening that gate to Markdown, the remedy that suggests itself, would still not have caught this. So the second gate keys on the KIND of claim instead of the kind of file. A count stated within 40 characters of a CLI constant that has a length is compared against `len()` of that constant, over tracked Markdown and over Python comments and docstrings alike; it fired on `CHANGELOG.md:5` before the correction and on nothing else in the tree. Unlike the anchor gate it verifies the number is CORRECT rather than merely dated, which it can afford because the constant is importable — no git plumbing, nothing that breaks on a shallow clone. It refuses more and relaxes nothing. What it does not close: a live-repository measurement stated in a Markdown file still has no gate at all, and `AGENTS.md` now says so rather than leaving the scope to be discovered by the next false number.

- Derives the toolchain-version gating partition instead of describing it, and states the coupling that made two readers treat one decision as two. Two independent reviews of this tree published two different and both-wrong lists of the verbs that drive roam without checking its version: one named `wire` as not delegating, when its entire body is a single call that delegates; the other dropped `wire` and still missed `unwire`. The partition is now computed from the call graph and pinned — `verify`, `claude` and `doctor` check the version, and seven other verbs (`baseline`, `init`, `report`, `run`, `stats`, `wire`, `unwire`) delegate to whatever roam is on PATH. Nothing changed about which of them refuse; a verb added later that delegates without gating now fails the pin until it is listed on purpose. Separately, `MAX_ROAM_MAJOR_EXCLUSIVE` now records that it GATES the envelope forward-compatibility machinery rather than sitting beside it: `_verify` exits on `_roam_problem` before it delegates, so every tolerance offered to a newer producer is reachable only for a same-major roam, and refusing the next major is a refusal the envelope layer cannot compensate for. Demonstrated end to end rather than reasoned about: a roam reporting a major above the ceiling is refused with the verifier never invoked, and the same envelope is accepted, disclosed or refused by the envelope layer only once the ceiling admits it.

- Names the field in the one forward-compatibility branch that still hard-refuses a newer producer, and corrects a refusal that claimed a floor the code does not enforce. `_require_known_shape` tolerates and discloses any unknown envelope key except one whose bare name is in `_VERIFY_INCOMPLETENESS_NAMES` — 33 names including `errors`, `warnings`, `capped`, `partial`, `stale` — which is refused outright so a producer cannot downgrade its own verification behind a rename. That trade is right and is unchanged. What was wrong is that the refusal named nothing: a roam that added a strictly neutral field called `warnings` produced `unknown_incompleteness_signal` with no field name, fell through to the generic protocol verdict, and told the reader their verifier "did not return one complete, bound Verify receipt v3" with a fix that prescribes upgrading roam — the component that is already ahead. The reason now carries the colliding name (filtered through the same safe-name renderer as every other disclosed field) and gets its own verdict that says what happened and points at the right side. Separately, the schema-incompatibility verdict said this build "reads roam-envelope-v1 1.1.0 and later same-major shapes"; `_envelope_schema_compatible` compares the major component only, so 1.0.0 is accepted too and the sentence was stricter than the gate it described. It now states the rule the code implements and reports 1.1.0 as what the build was written against rather than as a floor. Roam's real 1.2.0 additions (`matched_patterns`, `framework`, `framework_autodetected`, `framework_unknown`, `roi_band`, `context_lines`) are now pinned as accepted-and-disclosed and asserted to miss the tripwire vocabulary, so the day one of them collides is a discovery rather than an outage. What this does not close: the tripwire itself. A future roam field whose bare name is in that set still hard-refuses even when neutral, and no amount of disclosure changes that — it is a naming constraint that both sides of the contract have to know about.

- Requires a comment that states a quantity measured from this repository to name the commit it was measured at, and corrects the four claims that had already drifted. `prepush_leak_scan.py` said "the largest blob anywhere in this repository's history is 191 KB" — re-derived over `git rev-list --objects --all`, it is 202,290 bytes, and 191,307 was the same file two revisions earlier, so the number moves every time the largest file is edited. The same file said "0 binary blobs across this repository's 424 commits"; the count is 442 from HEAD and 452 across all refs, and the figure reproduced under no counting rule even when it was written — which `secret_scan.py` had already noticed and retracted *in its own file* while leaving the false number standing at its site. `secret_scan.py`'s own replacement numbers (51 candidates, 480 distinct blobs) had themselves drifted to 52 and 517. `cli.py`'s "~265 MiB" observation of a `claude` install measured 272 MiB. Retraction-by-adjacent-file is the shape here: the repository demonstrated it cannot fix this class by hand. Every drifted claim shares one mechanical property — it states a live-repo quantity with no anchor — and nothing could see any of them, because no runtime assertion, lint rule or reviewer diff reads a comment. `tests/test_measured_claims.py` now refuses a tracked `.py` comment or docstring that puts a measured quantity next to a live-repo referent without a commit hash within six lines, and `AGENTS.md` carries the rule. The trigger needs both halves: a quantity alone matches every captured scanner line in every fixture test, and a referent alone matches ordinary prose. A claim explicitly scoped to a past state ("before the fix", "when it was written") is already a dated observation and passes. While re-deriving, one incidental fact worth recording: five historical `CHANGELOG.md` blobs do carry a NUL byte, and they are read rather than skipped because `is_utf16_text` accepts NUL-padded content that is valid UTF-8 once the padding is removed — so the "0 binary" claim holds under the shipped classifier, and the bytes were scanned rather than passed over. What this does not close: the gate checks that an anchored number says *when* it was taken, never that it is still correct. Re-deriving each figure would need git plumbing per claim and would fail on a shallow clone, so an anchored-but-wrong number remains a reading problem.

- Separates the two ways `roam --version` can fail the toolchain inspection, which used to print the same sentence. `_inspect_roam` joins stdout and stderr and requires the result to be exactly one canonical version line, so a binary that printed a perfectly good version on stdout and a single deprecation line on stderr got the same verdict as a binary that printed garbage: "toolchain broken — `roam --version` returned no parseable version". That statement is simply false in the first case, and it sends the reader to reinstall a roam that is fine while the actual cause — a plugin, a wrapper script or a shell profile writing to stderr — is never mentioned. Reproduced deterministically: `_extract_roam_version` returns `14.0.0` for clean stdout and `None` the moment one stderr line is joined to it, in either order. Both streams are still required to be clean and the refusal is unchanged, because the version check is the one call this CLI trusts a stranger's binary for and a binary that writes anything alongside its version is not in a state worth vouching for. What changes is only the reason: when stdout alone carried a valid version and stderr carried N lines, the detail now says so and names the version it saw. Only the line count and the regex-validated version reach the verdict — untrusted output is never replayed. What this does not close: the inspection still refuses in that case rather than accepting the stdout version and reporting stderr as a warning. That would be a relaxation of an existing gate, which is a deliberate decision about how much noise a trusted-toolchain probe may tolerate, not a correction.

- Makes the toolchain-mismatch remediation name the direction the constraint actually resolves. The roam compatibility interval is closed at both ends (`>=13.10.0,<14`), so a mismatch has two opposite causes, and one printed fix served both: `python -m pip install --upgrade "roam-code>=13.10.0,<14"`. Below the floor that is exactly right. Above the ceiling — the state every roam major bump produces on a machine where roam and compile-code are installed separately — the same sentence describes the opposite of what happens. Measured directly, since the obvious guess is wrong in both directions: `pip install --upgrade "<pkg>>=a,<b>"` against an installed version above `b` exits 0 and *downgrades*, so the command does work; what is false is the word "upgrade", and what is missing is the second valid answer. A caller who wants to keep the newer roam was never told that moving compile-code forward is the other way out of the same refusal. The ceiling branch now says so in both directions and marks the pin as installing an older roam than the one on PATH; the floor branch is unchanged and pinned by its own test so the two cannot drift together. An absent or unparseable version — the `missing`, `timeout` and `broken` states, where no version was ever observed — falls back to the plain upgrade rather than being read as "above the ceiling". What this does not close: the ceiling itself. `MAX_ROAM_MAJOR_EXCLUSIVE` still refuses roam 14 and still has to be raised by hand for every roam major, before the envelope-compatibility logic that was built to answer exactly that question ever runs.

- Makes every refusal from a race between bounds report the reader's position on all of them, not only on the bound that happened to trip first. Two places in this repository run several limits over one loop and name only the winner. Explicit-directory traversal in `compile verify` is bounded by a directory count (20,000), an entry count (200,000) and a wall clock (10s); the GitHub CLI archive download is bounded by a per-read socket timeout (10s) and a wall-clock deadline (60s). In both cases which bound fires is a property of the user's hardware, not of policy — the crossover for traversal is exactly 20000/10.0 = 2000 directories per second, and the same 20,403-directory tree on the same machine was measured at 2071–2146 dirs/s on one day and 1586–1825 dirs/s on another, flipping the reported reason from `verification_directory_limit` to `verification_directory_timeout` with no code change in between. A message naming one bound therefore published a coin flip as if it were a diagnosis, and told the reader nothing about how close the other bounds were. Each refusal now carries its position on every axis — `verification_directory_timeout: 17412 of 20000 directories, 84119 of 200000 entries, 10.0s of 10 (~1741 dirs/s)` — and the product verdict renders it, so two users on different hardware read the same three facts and can predict the other bounds themselves. No constant moved and no branch refuses less; a raise site that carries no position still renders the bare bound. The download half also closes a branch that had no name at all: the per-read socket timeout surfaced as a bare `OSError` that escaped to the top-level handler and printed as a raw socket string with no statement of what was being fetched or how far it got, which is reachable by any link slower than roughly 238 KiB/s. What this does not close: the constants themselves are unchanged and still race, because no choice of numbers can make either bound dominate when the deciding quantity is the user's filesystem or link throughput. Tuning them is precisely the fix that reproduces on one machine and not on another.

- Raises the declared `click` floor from `>=8.0` to `>=8.3.3` and puts the runtime graph under the dependency audit that already covered the release toolchain. `click` below 8.3.3 carries CVE-2026-7246 / PYSEC-2026-2132, a command injection in `click.edit()` reachable through an attacker-controlled editor command; the fix landed in 8.3.3 and the advisory has no lower bound, so every version `>=8.0` admitted was affected. This package never calls `click.edit()`, but a dependency floor is a published claim about what a resolver may install into a user's environment, so it is raised rather than waived. Nothing in the repository could have found it: `audit-locks` queried the four hashed lock graphs — 66 rows of build, attestation, smoke and quality tooling — and the graph a user actually installs was queried by no gate at all. Measured before the change on the shipped tree: `audit-locks` reported `PASS (66 exact package versions)` while the same OSV service, asked directly about the floor that same `pyproject.toml` published, returned PYSEC-2026-2132 for `click==8.0`. The audit now also queries the inclusive floor of every declared runtime requirement, which is the oldest version the declaration admits and the only exact version a range names without a resolver — so the rule that this module never invokes pip is unchanged. An unauditable declaration is a refusal rather than a silent omission: a requirement with no `>=` floor, two floors, a partial version, an environment marker or an extra fails closed, because a requirement that names no version would otherwise contribute nothing to the query set and be indistinguishable from a clean one. What the audit does not cover is any version *above* a floor — that set is open and only the user's resolver knows which member it chose — and the printed PASS now says so instead of implying whole-graph coverage.
- Stops the tracked-tree scanners from reporting clean without reading anything. `scripts/check.py`'s `leak_scan()`/`artifact_scan()` and CI's `scripts/secret_scan.py` all derive their verdict from a `git ls-files` inventory, and a successful-but-empty inventory made every one of them an unconditional PASS. Both enumerations now strip Git's repository-redirection controls (`GIT_INDEX_FILE`/`GIT_DIR`/`GIT_WORK_TREE`, which a pre-push hook exports and which make `ls-files` answer about a different index and exit 0) and fail closed on an empty answer, matching the defence `_repository_state()` and the product's own git calls already applied.
- Makes `scripts/secret_scan.py` report a tracked symlink or an unreadable tracked file as a finding instead of skipping it, so the scan can no longer call content clean that it never decoded. `scripts/check.py`'s equivalent already reported both.
- Applies the leak catalogue to UTF-16 tracked files. Read as UTF-8 under `errors="ignore"` a UTF-16 file survives intact rather than failing — every NUL padding byte is itself valid UTF-8 — so a credential arrived as `g\x00h\x00p\x00_\x00…` and matched no pattern while the gate printed PASS. Windows PowerShell's `>` and `Out-File` emit UTF-16LE by default, which makes `gh auth token > token.txt` a concrete way a credential lands in a tracked file this scanner could not see. BOM-marked and BOM-less UTF-16 are both covered.
- Closes the same UTF-16 hole in **pushed history**, the gap the working-tree fix above recorded as still open. `scripts/prepush_leak_scan.py` shares the catalogue but decodes historical blobs itself, and its `b"\x00" in data` binary test dropped every UTF-16 blob before either catalogue saw it — so a credential committed in a UTF-16 file travelled to the remote while this gate printed clean, and purging history after a push does not un-publish it. Blob decoding now routes through the same `check._scan_views` rule the working-tree scanner uses, so the two gates cannot disagree about what is readable. Genuine binary (PNG, object files) is still not pattern-matched, pinned by a conservation test so a future "decode everything" cannot pass by burying the gate in noise.
- Stops a blob's SIZE from buying it a clean verdict in `scripts/prepush_leak_scan.py`. Blob decoding floored to an empty list of text views above a 4 MiB cap, and emptiness was the only channel it had: the scan loop then iterated zero times, so the unread blob was rendered as `clean` with exit 0, which `.githooks/pre-push` consumes as permission to push. Measured on the commit that added the blob, so range selection is not a confound, one byte decided it — 4,194,304 bytes blocked, 4,194,305 bytes clean, same credential. Padding defeated the gate, and not only for an attacker: any legitimately large asset (a generated dataset, a minified vendor bundle) carrying a credential anywhere in it pushed clean. A blob too large to scan is now UNANALYZABLE, a third state rather than a synonym for "no findings": it blocks with its own exit code, names the path and the size, and says why. Every blob is scanned regardless of size, in bounded line batches; the one remaining cap is an absolute ceiling that refuses loudly instead of skipping quietly, and is documented as a measured time budget rather than the memory guess the old cap rested on — a guess that was already false, since the batch object reader has the whole blob resident before the cap is consulted.
- Publishes the denominator behind every `scripts/prepush_leak_scan.py` verdict — blobs scanned, bytes scanned, blobs skipped, blobs unanalyzable — because `0 findings` is what a working scan of a clean range prints and also what a scan that read nothing prints. Skipped binary blobs are now named in the output rather than vanishing.
- Adds a positive control to every `scripts/prepush_leak_scan.py` invocation: a sentinel blob carrying one planted credential per catalogue, placed past a line-batch boundary, run through the same read-and-scan path real blobs take. If either plant is not found the scanner reports BROKEN and exits non-zero instead of reporting a clean range. This gate had already demonstrated it could report clean while reading nothing, so "0 findings" and "the scanner stopped working" needed to stop being the same output.
- Scans blob text in bounded line batches. Both catalogues match within a single line, so cutting on line boundaries changes no finding and no line number, while peak decoded memory stops tracking blob size (a 16 MiB blob: +23.0 MiB scanned whole, +0.5 MiB batched) and the line-number resolution in `check._leak_pattern_hits`, which is O(text) per match and therefore quadratic in a match-dense blob, is bounded to one batch (a 4.9 MiB match-dense blob: 50.9s to 5.7s).
- Stops `compile verify` from failing on an envelope that is valid and strictly richer than the one it was written against. The gate compared the producer's top-level key set for exact equality and its `schema_version` for exact string equality, so "the producer withheld a field we depend on" and "the producer is newer than us" raised the identical `envelope_contract` refusal — and roam's routine additive minor bump was enough to trigger it. This was not a future risk: roam-code 13.10.0 declares envelope `1.2.0` (`execution_contract`, `orchestration_contract`; both additive and absent when not carried), and against the real binary every `compile verify` refused with `envelope_contract`, exit 2, on an envelope whose key set matched ours exactly. The same exact pin sat in the launch-time hook attestation, where it reported `hooks:producer_attestation` on wiring that was canonical and current. Compatibility is now a major-version question, matching how the envelope is actually versioned; an unparseable or absent version stays a refusal, and an incompatible major gets its own reason and its own remedy (upgrade this package, not the producer, which cannot help).
- Discloses what forward compatibility ignored, rather than dropping it. A missing required key still fails closed; an unknown key is tolerated and named in the verdict block with the schema version that carried it, because silently ignoring unknown fields is how a receiver drifts out of sync with a producer and nobody notices. The disclosure is bounded and its names sanitised — an unrecognised field is producer-controlled text and must not be able to inject a line into a verdict. Nothing unreadable means no note at all: a line on every run of a newer producer would train readers to skip the one that matters. Tolerance covers only names that are unknown *and* neutral — an unknown field whose name asserts that something did not fully run (`skipped`, `not_run`, `degraded`, `warnings`, `list_counts`, …) is refused, so a producer cannot downgrade its own verification behind a rename and collect a clean pass. The request-bound `verification_receipt` stays closed, and known keys are still placement-checked everywhere, so opening the world to unknown names cost no existing gate.
- Stops `compile verify --changed` from handing roam its own live index as changed work. Changed-file discovery runs `git status --untracked-files=all`, which names every FILE inside an untracked directory, so any project that does not gitignore `.roam/` had `index.db`, `-shm`, `-wal`, `index.lock` and `index.state` bound into the verification scope. That scope can never verify — the WAL moves while roam reads it — so verify refused with `verification_incomplete`, exit 2, and prescribed `pip install --upgrade roam-code`, an upgrade that cannot fix a scope defect. Measured on a fresh repo with one edited source file: refused before, PASS on that one file after. The directory set that bounded traversal already used to refuse `.git`, `.roam`, `.venv`, `venv`, `node_modules` and `__pycache__` is now one shared constant applied to discovery too, because descent and discovery disagreeing about what source is was the whole defect. Only discovery narrows: an explicitly named path is the caller's stated intent and is verified or refused, never dropped. A narrowed scope is disclosed on its own line naming the count and the directories — from the constant, never the discovered paths, which are not replayed — and when narrowing leaves nothing, so that `--changed` falls back to roam's own discovery of the same tool state, the failure carries the remedy that actually works (`.gitignore`) instead of the one that does not.
- Stops `compile verify` refusing an ordinary changed set that includes a documentation file. Roam's scope block reports `unresolved_file_count` as targets minus the indexed file map and omits the key at zero, while `non_code_file_count` counts doc surfaces among the same targets whether or not they resolved; the two are independent. This gate required `non_code_file_count <= unresolved_file_count` and at least one unresolved file, which encodes the opposite belief — that a doc is never indexed. Against roam-code 13.10.0, the pinned floor, a changed set of `README.md` plus two Python files produced `target 3 / indexed 3 / non_code 1` and was refused as `scope_binding`, exit 2, on this repository's own tree. The accounting still has to close exactly: the target count must match the request, `indexed_file_count` must equal `files_checked`, indexed plus unresolved must equal the target count, and the block must exist for a reason.
- Stops the scope-instability refusals prescribing a roam upgrade. `post_verify_content_changed` and `post_verify_scope_changed` are raised by this CLI's own post-run recheck, never by roam's receipt, and roam's version was already proven in range before verify ran — so the remedy now names the actual cause (something is writing to the worktree) and the actual next step.
- Stops all three leak scanners deciding "do not open this" from a file NAME. Each carried a suffix list — `.png`/`.jpg`/`.gif`/`.ico` in `scripts/check.py`, a longer one in `scripts/secret_scan.py` that `scripts/prepush_leak_scan.py` shared — and a file name is not a measurement of the bytes behind it. Measured on the shipped scanners: a plain-text file carrying an AWS access key and committed as `logo.png` produced `prepush_leak_scan: clean (1 commit(s) scanned, 0 findings; blobs: 0 scanned / 0 bytes, 0 binary-skipped, 1 path-filtered, 0 unanalyzable)` with exit 0, `check.leak_scan()` printed PASS beside it, and `secret_scan` reported `candidates=2 examined=1 findings=0`. Because `.lock` sat in that list next to `.exe` and `.dll`, all four `release/*.lock` files — plain-text pip requirement files, and the natural home for an `--index-url` credential — were opened by no scanner at all; they are clean today, so this was a hole rather than a breach. Binary is now decided from the content by one shared rule (`inventory.is_binary_content`, BOM-aware so the UTF-16 fix is preserved), and genuine binary is still not pattern-matched, pinned by conservation tests in all three scanners so this cannot become "decode everything" and bury the gate in noise. The real tree went from 46 to 50 files actually read out of 51 candidates.
- Gives `scripts/check.py`'s narrow catalogue a pattern for the credential this repository publishes with. A PyPI upload token is what an `--index-url` line in a lock file would carry, `secret_scan`'s catalogue already had it, and the one gate that did read those files had no pattern for it — so a token there passed all three gates: unread by two of them and unmatched by the third.
- Acts on the denominator instead of only printing it. `prepush_leak_scan` published blobs and bytes read but reported `clean` regardless of them; `secret_scan` printed `examined 0 text files` and exited 0; `check.leak_scan()` published paths CONSIDERED, which reads identically whether every one was opened or every one was skipped unread. A range that changed paths while no blob was opened is now a refusal that names the paths (exit 3), a tree scan that read no candidate's content refuses rather than passing, and the leak gate publishes files READ alongside paths established.
